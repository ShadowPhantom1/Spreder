01 — OVERVIEW

BHNSTOCK SMS SPREADER 3D WEB is a campaign command-center that turns a fleet of Android worker devices (each mirroring state into a Firebase RTDB) into a high-throughput SMS fabric. Operators create campaigns with templated messages (Hello {{name}} … {{phone}}), import contacts (phone + vars), and launch. The server fans messages out in waves across online devices round-robin, queues via RTDB REST, waits for ACK, retries once on timeout, and streams live progress over WebSockets.

Multi-Hive
Many Firebase DBs under one roof. Per-hive health, latency, device counts.
Wave Dispatch
Batch + delay tunable. Round-robin balances load. Pause/Resume/Cancel live.
ACK Chase
ACK timeout 15s default. Retry once, then mark failed. Device counters.
Live UI
Socket.io pushes: campaign:progress, message:sent/failed, devices:update.

KEY BEHAVIORS
  • campaign_messages.rendered is template baked with {{name}} {{phone}} {{custom}} at creation — avoids re-render on retry.
  • queue_items mirrors pending work; engine pulls LIMIT batch_size WHERE status='queued' per wave.
  • All writes that fan out (campaign create) run inside db.transaction().
  • Admin seeded on boot via ADMIN_USER / ADMIN_PASS (bcrypt).

04 — FIREBASE SERVICE (REST, NO ADMIN SDK)

File: src/server/services/firebaseService.ts — pure fetch against RTDB REST. Mock-aware: any URL containing mock|demo|bhnstock|example synthesizes devices & ACKs for instant demos.

MethodREST / LogicDetails
testConnection()GET <url>/.json?shallow=true or mockMeasures latency, returns {ok, latencyMs, message}
pollDevices()GET <url>/devices.json → map to {id,name,model,status,battery,signal}Falls back to deterministic seeded synthetic pool (4–8 devices) if fetch fails or mock URL
queueSms()PUT <url>/queue/{deviceId}/{messageId}.jsonMock path adds 180–350ms delay + 8% simulated fail
waitForAck()Simulated + real-ready600–1200ms → 82% delivered, 10% failed, 8% timeout. Honors timeoutMs
seedDevicesIfEmpty()Ensures poll returns a poolUsed by UI “SEED” button
SYNTHETIC DEVICE LOGIC
hash = hashCode(firebase.id); count = 4 + |hash|%5; model = MODELS[(|hash|+i) % MODELS.length]; online = seededRng(seed + i*100 + now/5000) > 0.18; busy = online && rng() > 0.85; battery = 22 + rng()*78; signal = 55 + rng()*45;

Why REST? No service-account friction; works with any RTDB URL, shallow checks are cheap. Real deployments can swap in Admin SDK by replacing these four functions — the rest of the system stays unchanged.

05 — QUEUE / CAMPAIGN ENGINE — THE WEB SHOOTER

File: src/server/services/queueService.ts — single-process, in-memory run-state, durable queue in SQLite.

Campaign Draft
contacts → dedupe → rendered → queue_items
queued × total → processCampaign()
wave loop → dispatchItem()
queueSms → waitForAck → done / retry / failed
socket emits
CREATE CAMPAIGN
  • Dedupe by normalized phone (^\+?[0-9]{7,15}$), skip duplicates, collect invalid.
  • Render template once per contact: {{name}} {{phone}} {{var}} via regex replace.
  • Insert campaigns( pending=total ) + campaign_messages( pending ) + queue_items( queued ) in one transaction.
  • Emit campaign:created.
renderTemplate(tpl, vars, phone){ tpl.replace(/{{phone}}/gi, phone) .replace(/{{name}}/gi, vars.name||'there') .replace(/{{key}}/g, vars[key]) }
WAVE LOOP (ROUND-ROBIN)
state = {cancelled:false, paused:false} // per campaign batch = campaign.batch_size || settings.dispatch_batch_size // default 5 delay = campaign.delay_ms || settings.dispatch_delay_ms // default 1200 while(!cancelled){ if(paused) await sleep(500) pending = SELECT … LIMIT batch WHERE status='queued' if(!pending) break devices = SELECT * WHERE status IN ('online','busy') // fallback: any 5 for each msg in pending (parallel wave): device = devices[rrIdx++ % devices.length] UPDATE queue_items → dispatching, messages → sending (+attempts) emit message:sending await queueSms(device, payload) ack = await waitForAck(timeout=ack_timeout_ms) if ack.ack → sent/done, sent++, pending--, device.total_sent++ else if attempts<2 && ack.status!='failed' → requeue queued/pending else → failed, failed++, pending--, device.total_failed++ emit message:sent|failed|retry emit campaign:progress {sent, failed, pending, total} await sleep(delay) } → completed if pending==0 else paused/cancelled
CONTROL SURFACE
OpWhatGuard
startSets running, fires processCampaign (fire-and-forget)Not already running/completed/cancelled
pauseFlips paused=true, DB status=pausedIn-memory flag + DB row
resumeClears paused, status=running, restarts loop if neededHandles cold resume (not in memory)
cancelcancelled=true, status=cancelled, deletes run-stateLoop exits next tick

Concurrency: one loop per campaign (Map<campaignId,state>). Waves fan out with Promise.all per batch; cross-campaign concurrency is sequential per campaign but parallel across campaigns.

06 — DEVICE POLLER

File: src/server/services/devicePoller.ts — interval sweeper, Socket broadcaster.

attachIO(io) → interval = setInterval(pollAll, poll_interval_ms) // default 5000 pollAll(){ for each firebase in firebases: devices = await firebaseService.pollDevices(fb) upsert devices (ON CONFLICT id DO UPDATE) UPDATE firebases SET device_count, status='online' io.emit('devices:update',{firebaseId, count, devices:slice(0,8)}) io.emit('firebases:update',{id, device_count, status}) io.emit('stats:devices',{online, offline, busy, total}) }
  • Starts on server boot; auto-seeds demo hive if table empty.
  • Upsert uses INSERT … ON CONFLICT(id) DO UPDATE to keep phone/battery fresh without losing counters.
  • All intervals read from settings table (live-tunable via Settings page).

11 — IMPLEMENTATION — RECREATING CLEANLY

This repo is the clean rebuild. Every layer above is implemented in the file tree. To reproduce from scratch:

# 1) scaffold npm create vite@latest -- --template react-ts npm i express better-sqlite3 bcryptjs cookie-parser cors jsonwebtoken socket.io socket.io-client zod npm i -D tsx concurrently @types/node @types/express @types/better-sqlite3 @types/bcryptjs @types/cookie-parser @types/cors @types/jsonwebtoken npm i react-router-dom lucide-react framer-motion recharts clsx tailwind-merge npx tailwindcss init -p # 2) copy src/server/* + src/client/* from this project # 3) configure vite.config.ts proxy: proxy: { '/api':'http://localhost:3000', '/socket.io':{target:'http://localhost:3000', ws:true} } # 4) env (or rely on defaults in config/index.ts) PORT=3000 JWT_SECRET=change-me-32chars-min ADMIN_USER=admin ADMIN_PASS=admin123456 DATABASE_PATH=./data/sms.db # 5) run npm run dev # :5173 (vite) + :3000 (api) # production npm run build && npm start # serves dist/client via express.static
CRITICAL LOGIC TO KEEP
  • Dedupe + template render at create-time (not dispatch-time).
  • Transaction wrapping campaign inserts.
  • Round-robin index surviving across waves.
  • Re-queue on timeout (attempts<2) else fail — preserves at-least-once without spam.
  • Poller upsert + firebases device_count sync + io emits.
  • Auth reads both cookie and Bearer for flexibility.
SPIDEY UI CHECKLIST
  • Tailwind tokens spidey.* + halftone + web-pattern utilities.
  • Layout header web gradient line (red→yellow→cyan).
  • Cards: card-3d hover tilt + comic-border + halftone watermark.
  • Hero concentric web circles + halftone + glass KPI tiles.
  • Login giant web SVG (0.04 opacity) + mask logo.
  • Empty states: “shoot your first web 🕷️”.
WHAT’S WIRED vs MOCK

Firebase layer is REST-ready: point database_url at a real RTDB and pollDevices/queueSms/waitForAck will hit live endpoints. The mock fallback (URL contains mock/demo/bhnstock/example) keeps the demo fully functional without credentials — latency, online ratios, battery/signal all stay realistic so the 3D UI feels alive.
